# 周围玩家数据模型显示抓取报告（官服 fxgame.exe）

> 抓取对象：官服客户端 fxgame.exe（苏州场景，人堆）
> 抓取时间：2026-09-11 23:45 ～ 2026-09-12 00:11（两轮，共约 18 分钟）
> 服务目标：为 9yin-go-server2 实现**假人系统**——只需要"玩家数据显示 + 外观模型显示"
> 解码输出：38315 帧、0 解码错误；官服 2426 项属性协商表全量拿到

---

## 〇、结论摘要（给假人系统的一句话定论）

1. **官服周围玩家不走 0x0D 对象创建、也不走视图通道**，走的是 `0x2C 批量移动 + 0x2D/0x2E 属性KV批量` 同步族，以 (objID, ownerID) 二元组引用对象；**移除 = 0x0E（9 字节）**。
2. 但**我们服务端现有 0x0D 玩家归档路径（sendPlayerSpawn/addObject）客户端是认的**——真玩家互见已长期验证。假人系统**最小可行路径 = 复用现有 0x0D 玩家 spawn 路径**，填齐外观属性即可显示模型，不需要先实现 0x2C 批量通道。
3. **客户端按属性"名字"绑定，不按下标数值**（0x09 协商表按名字+线型协商）。官服 2426 项表的关键下标仅作对照参考，我们自己的表编号不必对齐。
4. 外观模型显示必填属性（名字绑定）：Type/Sex/Photo/Face/Hair/School/NewSchool/Cloth/Pants/Shoes/Weapon/WeaponName/WeaponMode/ActionSet/Name(widestr)/Level/MoveSpeed 族/State。Buff 显示走 BufferInfo1-15 = 逗号分隔 hex ID 串（官服实测 `"1EA1,E0A0EC6,5735C95,8,0,0"`）。
5. 周期行为：官服 0x2C 约 200ms 一批；C2S 0x0A 每秒一帧（16B 会话前缀+递增计数器=时序同步帧，非 ack）；同 ID NPC 的 0x0D 每 30~60s 重发；0x06 伴生帧可省。

### 1.1 环境

- 官服客户端 fxgame.exe，本机 192.168.0.102，Wireshark 工具链（dumpcap/tshark/capinfos）在 `C:\Program Files\Wireshark\`。

| op | 语义 | 备注 |
|---|---|---|
| 0x04 | login-success | |
| 0x06 | 伴生帧（len=1） | 与 0x0D 成对出现，**可省略** |
| 0x09 | 属性类型协商表 | count u16 + (名字\0 + 线型 byte)*，官服 2426 项 |
| 0x0A | record schema | 过图时一张 10429 字节帧注册 **446 张表**；C2S 方向每秒一次=时序同步帧 |
| 0x0C | exit-scene | |

## 三、核心发现：周围玩家同步帧族（0x2C / 0x2D / 0x2E）

### 3.1 反证：玩家不走 0x0D、不走视图

- 全程 62 个 0x0D 逐帧解码，**全部是 NPC 族**（Type=4：物品NPC/克隆NPC/宠物/宝箱/年兽火），没有一个周围玩家。
- 全程 39 个 create-view（0x15）全是物品/技能目录视图，与玩家显示无关。
- 周围玩家的出现与移动全部由下面三个 op 承载，均以 **(objID u32, ownerID u32)** 二元组引用对象（如 `235540166-91446421`）。

### 3.2 0x2C 批量移动（~200ms 周期）

- 头部：`2C 47` + u32（=帧长-1，实测 len=290 帧此值 0x121=289 ✓）+ u32（计数/时序）+ float32 **-0.0**（`00 00 00 80`）+ u16 条数。
- 每条：objID u32 + ownerID u32 + 约 9 个 float32（X/Y/Z/朝向/速度分量）。
- 周期约 **200ms** 一批，把视野内所有移动中对象的位置打包下发。
- 原始样本（`_2cde.txt`）：`2c472101000062010000000000800800ae3c070e4d1dae05abbecd43d632a040...`（首条 obj=0x0E073CAE owner=0x05AE1D4D，X≈409.5 Y≈5.01 Z≈756.4）。

### 3.3 0x2D / 0x2E 属性KV批量

- 0x2D：count u16@1 + 每条 (objID u32 + ownerID u32 + kvcount u16 + (key u16 + value)*)；**值类型按 0x09 协商表线型解释**。
- 0x2E：同 KV 批量但带 0x2C 式头部（`2E 46/47` + u32 + u32 + u16）。
- 实测键（官服下标）：470=MPRatio、469=HPRatio、467=SP、471=InParry、478=ParryRatio、**632/636/640/642=BufferInfo4/8/12/14**。
- **BufferInfo 值格式（重要）**：逗号分隔 hex ID 串，如 `"1EA1,E0A0EC6,5735C95,8,0,0"`（buff静态ID hex 串 + 数字尾段），可直接对照我们 BufferListStr 的拼法。
- 触发时机：不定期，随状态变化批量补发（进出战斗、buff 增删、血蓝变动）。

### 3.4 配套帧

- 0x10 对象属性更新：单对象 KV 归档（同我们 object_property.go 的 0x10 帧头布局一致）。
- 0x1F location（25B）/ 0x21 完整移动块：离散位置与完整移动。
- 0x0E 移除：`0e + objID u32 + ownerID u32` 共 9 字节（`body=0ede6a010e307dbd05` → obj=0x016ADE0E? 按小端解析，owner 随后）。

## 五、过图/场景加载时序（实测 00:09:52-00:10:07）

1. **S2C 0x0A 大 schema 帧**：单帧 10429 字节，注册 **446 张 record 表**（self_home_rec/neighbour_rec/Task_Accepted(28列)/Task_Record(15列)/HomeFurnitureRec/BannerNpcRec 等）。前 30 张表序见附录 B。
2. **S2C 0x15 建视图族**：174-181/2/3/121-126（背包，与我们 starterBagViews 一致）、40/41/43-48（技能/内功/轻功目录）、cap 512/800 大视图。
3. **S2C 0x09 属性协商表**：2426 项（与 0x0A 同秒到达）。
4. **S2C 0x0D NPC 对象爆发**：视野内 NPC 逐个创建（16-20 个属性/个），**同 ID NPC 每 30~60s 重发一次 0x0D**（实测 obj=234894167 在 00:10:10、00:10:31、00:11:08 三次重现）。
5. **C2S 0x0A 每秒一帧**：16B 会话前缀 + 递增计数器（`...d801 0002 0002 9c03 0000 03xxxxxx02 00000000`）= 客户端时序同步帧，**不是 ack**，服务端收到忽略即可。

> 注：record schema 服务的是 UI 面板（任务/家园/声望等），**玩家/假人的场景显示不需要 record 通道**。

## 六、custom 消息（0x1E TVarList）实测语义

TVarList 布局：u16 count@1；参数类型字节 2=int32/3=int64/4=f32/5=f64/6=string(u32 len+1+bytes+\0)/7=widestr(u32 (len+1)*2+UTF-16LE+\0)/8=object(objID+ownerID)；**首参=消息ID**。

| msgID | 语义 | 实测样本 |
|---|---|---|
| **20** | 播招/动作 | `n=6: 20, obj:235982037-96104843, str:chz_03_1, obj:235495714-95563926, int32:0, f32:0.00`（obj+动作名+目标+flags） |
| **18** | 受击反馈 | `n=3: 18, obj:..., str:hurt_f_1_l_half` |
| **24** | 动作/伤害 | `n=4: 24, obj:..., int32:40, str:ng_yg_707`；长版 n=13 含目标+伤害值 f32:30.00 |
| **205** | 特效广播 | `n=4: 205, obj:..., str:CS_jh_chz04, obj:目标`（CS_jh_* 特效名） |
| **337** | 坐标广播 | `n=7: 337, obj:..., f32:465.65, f32:1.10, f32:759.90, f32:-0.12, int32:0`（obj+x,y,z+orient+flag） |
| 294 | 时间同步 | `n=5: 294, int64:37047635, int64:13433702155517, int64:1789228555, f64:46277.99...` |
| 711 | 奇遇事件 | 含玩家名宽字符「徐多郁」、sns_event_text_8;book_qinggong_5 |

> 假人想"看起来在打拳/跳舞/待机"，用 msgID=20（动作名）+ 205（特效）即可；动作名形如 `wuji_CS_jh_myjf05`、`chz_03_1`、`fwz2_CS_jy_xsd05`（前缀=动作集分类）。

## 七、周期行为汇总

| 行为 | 周期 | 说明 |
|---|---|---|
| 0x2C 批量移动 | ~200ms | 视野内所有移动对象位置打包 |
| C2S 0x0A | 1s | 客户端时序同步，服务端忽略 |
| NPC 0x0D 重发 | 30~60s | 同 ID NPC 定期重发创建帧 |
| 0x2D/0x2E KV 批 | 不定期 | 随状态变化（战斗/buff/血蓝） |
| 0x06 伴生帧 | 随 0x0D | len=1，可省略 |

## 八、假人系统实现清单（Go 服务端落地）

### 8.1 最小可行路径（推荐，一天内可落地）

**复用现有玩家 spawn 路径**（`player_actor.go:3095` addObject 0x0D 玩家归档 + `main.go:4321` serverLocation 0x1F）：

1. 为假人分配 objID（u32 对：objID + ownerID；可复用玩家分配器或独立段位）。
2. 构造一个"假人档案"（configJSON：名字/性别/门派/等级/外观五件套/武器/称号），走与真玩家相同的 0x0D 归档编码。
3. 进入场景：0x0D 创建 + 0x1F 位置 → 周围真玩家客户端即显示假人模型与头顶信息。
4. 状态显示：0x10 补 State(183)/HPRatio(469 族)/BufferListStr。
5. 离开场景：**0x0E（9 字节：op+objID+ownerID）**——对照我们现有对象移除路径确认已用 0x0E。

### 8.2 必填外观属性（名字绑定，缺了模型显示不对）

- 基础：Type、Sex、Photo、Face、Hair、School、NewSchool、Force、Name(**widestr**，注意 UTF-16LE 编码)、Level、TitleID、Camp。
- 模型五件套：Cloth / Pants / Shoes / Weapon（官服是 string 资源名；与我们 pushGearVisual 的模型通道对齐）。
- 武器显示：WeaponName / WeaponMode。
- 动作：ActionSet + 待机站姿（遵守项目约定：恢复待机一律 `currentIdleStanceAction()`，勿写死 stand）。
- 移动：MoveSpeed/WalkSpeed/RunSpeed/SpeedRatio（影响客户端插值）。

### 8.3 显示增强（可选）

- **Buff 图标**：BufferInfo1-15 = 逗号分隔 hex ID 串（官服 `"1EA1,E0A0EC6,5735C95,8,0,0"` 格式），经 0x2D/0x10 下发。
- **动作表演**：custom msgID=20 播招 + 205 特效；坐标跳转用 337 或 0x21。
- **平滑行走**（如需）：实现 0x2C 批量移动通道（~200ms 周期）；静态假人用 0x1F/0x21 离散更新即可。
- 假人头顶血条：HPRatio(469 族) 默认 100。

### 8.4 与官服的差异说明

- 官服玩家走 0x2C/0x2D/0x2E 通道而不发 0x0D；我们走 0x0D 玩家归档，**客户端两路都认**（真玩家互见已验证）。0x2C 通道可作为后续优化项，不是显示门槛。
- 属性下标不必对齐官服——客户端按 0x09 协商表名字绑定；但**名字拼写必须与客户端期望一致**（Name/Cloth/BufferInfo…）。
- record schema（446 表）与假人显示无关，无需扩展。
