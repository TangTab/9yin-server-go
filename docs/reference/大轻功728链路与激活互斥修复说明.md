# 大轻功 728/729 链路上报 + 面板激活互斥修复说明

**日期**: 2026-09-14
**涉及文件**: `cmd/protocol-probe/main.go`、`cmd/protocol-probe/qinggong_records.go`、`cmd/protocol-probe/player_actor.go`、`cmd/protocol-probe/qinggong_records_test.go`、`cmd/protocol-probe/yufeng_wind_test.go`

## 一、根因 1：大轻功链动作走 C2S 728/729，服务端从未处理

官服抓包（官服大轻功抓取报告.md，2026-09-12）实证：现代客户端在御风/大轻功状态下，
二段跳（腾跃 qinggong_20）与空中冲刺/滑翔（qinggong_24）**不发 216**，而是发：

```
0x0A TVarList(728, "qinggong_20")                    ← 首次腾跃
0x0A TVarList(728, "qinggong_24") ×3                 ← 空中冲刺/滑翔段
0x0A TVarList(729, "qgskill_gj_air_rush_1_typ7", 10.46) ← 冲刺特效请求
0x0A TVarList(729, "QG_JH_gj_001")                   ← 当前激活大轻功
```

官服把每条 728 当作链动作「开始」，每段冲刺后重发 `buf_qg_gliding`（0xA9 通道，
尾 flag 0x800）。本服 0x0A activity switch 没有 728/729 分支，帧被静默丢弃 →
客户端原生 BuffStore 永远收不到滑翔 buff → **进不了腾跃/滑翔状态**。
机制与踏水行同类：引擎按 buff 判定状态。

### 修复（main.go）

- `handleQingGongActionCustom`（728）：动作名限 qinggong_20..25，规范化成
  `(216, 动作名, marker=0)` 复用整条已验证的 216 链动作接受路径（扣 GJ 轻功点、
  链路状态推进 358-362、链 buff 0x10+0xA9 双通道、到期调度）。
- `handleQingGongEffectCustom`（729）：登记特效请求；识别 `qgskill_gj_air_rush*`
  时调 `refreshGJGlidingBuff` 按官服语义刷新滑翔 buff（仅链路活跃时，复用动态槽）。
- 0x0A activity switch 与 standalone 0x1E/0x27 直发 switch 两处均注册 case。

## 二、根因 2：面板激活不是单槽互斥

`form_wuxue_qinggong.lua` 的 `on_btn_active_click`（L171-186）只是 toggle：
按钮态 `IsActive = check_qgskill_is_avtive(id)`，而该函数按
**ActiveQGSkillRec 任意行 col0 匹配**（form_wuxue_util.lua）。客户端自身不做互斥，
**一次只能激活一个大轻功的约束必须由服务端保证**。

旧实现每次激活都发 `0x11 add-row(行2)`。客户端记录表对重复 add-row 会**追加重复行**，
于是每次切换激活都攒一行：历史激活全部被判成激活态（按钮停在「关闭」=sub 2，
引擎行 2 读取也随之错乱）。日志实证：`217 sub=2 "QG_JH_gj_003"`——用户点切换时
客户端却发「关闭」。

### 修复

- `playerActor.replaceActiveQingGong(id)`：激活集合整体替换（官服单槽模型）；
  重复激活当前唯一 ID 返回 false 不重发。
- `playerActor.activeQingGongSlotCreatedOnce()`：行 2 每场景会话只允许一次
  `0x11` 建行；之后切换一律 `0x13` 原地覆写行 2 col0（与官服抓包字节级一致）。
- `grantDefaultActiveQingGong`：登录/SwitchScene 时重置建行标记（客户端记录表
  重建后需要重新 0x11）。
- 关闭（sub 2/7）后行 2 col0 覆写为空串 → 所有按钮回到「激活」态。

## 五、追加轮（同日晚）：「激活没反应」——行 2 建行方式与 grant 早退

互斥修复上线后实测：客户端发 `217 sub=1 "QG_JH_gj_001"`，服务端回
`activated ... via ActiveQGSkillRec`（changed=true，说明该会话 grant 没把
001 写进集合/客户端没吃到行），但**面板按钮毫无变化**。

### 根因 1（核心）：空表直写行 2，客户端拒收

结合本仓库多条**已被真实客户端验证**的记录语义
（Task_Completed 稠密倒序下发 + 测试里的 insert-at-row-zero 模拟、
QingGongRec 18 行全部 [12:14]=0 逐条插入、官服 cooldown_rec「0x11 写
目标行 36 → 0x13 填格」），0x11 SERVER_RECORD_ADD 的 [12:14] 是
**插入行号：写行 N 要求行 0..N-1 已存在**。

`writeActiveQingGongSlot` 旧写法直接往**空表**插行 2 → 客户端越界拒收 →
ActiveQGSkillRec 行 2 **在客户端侧从未存在** → 后续所有 0x13 row=2 改格
全部落空 → `check_qgskill_is_avtive` 永远 false（form_wuxue_util.lua
L1589 还要求 `FindRecord` 两表至少一表存在）→ 按钮永远「激活」态、点了
也看不到变化。官服抓包只抓到中段切换（0x13 覆写已存在的行 2），从未抓到
登录期建行帧，所以此前没暴露。

### 根因 2：grant 重登早退，一帧不发

`grantDefaultActiveQingGong` 走 `activateQingGongRecord`，重登（同进程、
同 playerActor、激活集合已是 {QG_JH_gj_001}）时 `replaceActiveQingGong`
返回 changed=false → **早退且一帧不发** → 新连接（客户端记录表刚重建）
永远收不到槽位块 → 点激活也是 changed=false 静默无帧。

### 修复（qinggong_records.go）

- `writeActiveQingGongSlot` 重写：先以**空串 0x11 建占位行 0/1/2**
  （对 0x11 的插入行号/追加/覆写三种语义均成立），再用 **0x13 record-grid
  覆写行 2 col0 = id**（纯索引寻址，官服字节级写法）。
- `grantDefaultActiveQingGong` 改为**强制路径**：reset 建行标记 →
  `replaceActiveQingGong`（返回值忽略）→ `writeActiveQingGongSlot`
  （无条件下发）→ `activeQingGongSlotCreatedOnce()` 置位。每次登录/0x0C
  重入都完整重发槽位块。
- 单槽互斥下 `deactivateQingGongRecord` 的「覆写为剩余最近激活 ID」分支
  实际恒为空串（集合至多一个 ID），行为不变。
- 测试同步更新：首次激活=4 帧（3×0x11 空占位 + 1×0x13）；切换/再激活=
  单帧 0x13；新增 `TestGrantDefaultActiveQingGongForceResendsSlotRows`
  （重登必须原样重发 4 帧）；`TestActiveQingGongCustomSubClose` 按互斥
  语义重写（关闭=清空槽位，行保留）。

### 附带影响（重要）

引擎原生侧固定读**行 2** 取「当前大轻功」（第十一轮定案）。行 2 此前在
客户端从未存在，意味着**二段跳进腾跃的门判定同样读不到激活的大轻功**——
「双击空格不进腾跃」很可能与此同根因。重测时两项一起验证。
