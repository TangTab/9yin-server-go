# 大轻功（御风）修复说明

日期：2026-09-12（第十一轮更新：官服抓包尾端「切换激活大轻功」帧解码——ActiveQGSkillRec 行 2 槽位覆写，旧实现追加行/行号恒 0 导致引擎读不到激活态）

## 第十一轮：大轻功激活记录写法修正（本轮修复）

用户指认官服抓包尾端有其「切换激活其他大轻功」的帧。解码 hot.log 尾端
（1789144692 时间窗）拿到官服激活/切换大轻功的**权威写法**：

1. **官服帧**：玩家切换激活 QG_JH_gj_001 → 002 → 006 时，服务端各发一条
   **0x13 record-grid** 帧：`recordIndex=117(官服表) row=2 column=0
   value=字符串"QG_JH_gj_00X"`——覆写式切换，**从不删行、从不追加行**。
   行 2 就是「当前大轻功」槽位（行 0/1 疑似初级/中段槽位）。
2. **本服旧实现错在哪**：`activateQingGongRecord` 用 0x11 record-add 追加
   行，且 [12:14] 行号字段**恒写 0**（旧注释误标为"first column"）。而
   record schema 表是登录时按名字下发给客户端绑定的（serverRecordTable，
   索引 1=ActiveQGSkillRec 没错），错的是**行号**——引擎原生侧固定读
   行 2 时永远读不到激活状态。这就是「大轻功没有真正激活」的根因。
3. **佐证解码**：官服同窗的 record 109（cooldown_rec，col0=27042 正是
   ride_windrunner 的 CoolDownCategory）用「0x11 加整行（[12:14]=目标行
   36）→ 0x13 填格」模式，证明 0x11 的 [12:14] 是**目标行号**。
4. **修复**（qinggong_records.go / player_actor.go）：
   - `qingGongActiveSlotRow = 2` 槽位行常量；
   - `serverRecordAddStringRow`：0x11 带显式行号（旧 serverRecordAddString
     保持行 0，不动已验证记录）；
   - 激活（GM 默认 + C2S 217 sub=1）：0x11 写行 2 + 0x13 改格行 2 col0
     （与官服字节级一致）；
   - 取消（sub=2/7）：不再 0x12 删行，0x13 覆写行 2 为剩余最近激活 ID
     （无剩余则清空）；player 新增 latestActiveQingGong。

fxgamelogic 反汇编旁证：0x1284E5F0（QingGongRec 按名 FindRecord 谓词）、
0x12A1B1B0（shortcut_rec/cooldown_rec 名字过滤链）——客户端按名字解析记录，
但**行号语义是绝对的**，槽位必须写在官服同款行上。

## 第九轮：蓄力完成对话（C2S 249 WIND_HOLD_POWER_END）

第八轮一次性下发全部流程帧后实测仍失败，且现象变化：客户端**从"发
qinggong_9"变成"零 216"**，只多发一条空 msg249。第九轮三路合围拿到定论：

1. **客户端 Lua（form_yufeng_power.lua + client_custom_define.lua）**：
   - `CLIENT_CUSTOMMSG_WIND_HOLD_POWER_END = 249`；
   - msg25 的首参 **2000 = 蓄力条最大值**（server_open_power_skin 的
     max_value），后两个字符串是流程动作名；
   - 蓄力条满（power_time 达 max）→ 客户端 `CustomSend(249)` 上报 →
     `nx_pause(2)` → 关表单。**249 就是"蓄力完成"信号**。
2. **官服抓包方向核对**：frames.log 中客户端上行只有 0x0A/0x18（御风
   触发走的文本通道），官服 S2C 序列里真身 buff 出现在 ready buff 约
   2s 后——正是客户端蓄力条满、发 249、服务端应答的对话间隔。
3. **fxgamelogic.dll 反汇编（字节级 rip 引用扫描）**：
   - 引擎字符串 `on_yufeng_hold_power`（Lua 名字路由）、`HoldPowerTime/
     WindMaxSpeed/WindFixSpeed/MaxWaitTime`（引擎直接读 tool_item.ini
     的御风道具节，0x86b=ItemType 2155 校验在 0x1157C960）；
   - 大轻功疾跑状态机 0x11C2AED0：`[实体+0x38]` 动作对象存在 +
     **+0x5B8 == 2** + BufferStore `HasBuff("buf_ride_yufeng")`（vtable
     +0x2F8）+ 动作名/`grd_` 前缀检查 → 构建 `qg_fastruning`；
   - 引擎引用 `buf_ride_yufeng` 共 4 处（含 0x1284EB60/0x1284F2D0 两道
     已知门槛）。

### 根因

第九轮前把真身 buff 与蓄力开始帧**一起发**，客户端流程态被打乱：蓄力条
照常走完并发了 249（02:20:22），但服务端没有 249 处理器，真身 buff 的
0xA9 在蓄力开始时就被吞进流程态，二段跳门槛（原生 BuffStore + 流程动作
对象双条件）始终不成立。

### 本轮代码修复（yufeng_wind.go 重写 + main.go 两处分发）

1. **两阶段拆分**：`sendYufengChargeStart`（msg25/26 + 0xA9 ready 加 +
   msg469 + msg1 11610）与 `sendYufengChargeComplete`（0xA9 真身加 +
   ready 删 + msg1 11611 + 启动 5s msg24 保活）。
2. **新增 C2S 249 处理器** `handleYufengHoldPowerEndCustom`：收到蓄力
   完成上报 → 补发阶段二；重复上报/无待完成状态时忽略。挂入 main.go
   的 activity(0x0A) 与 standalone(0x1E) 两处 C2S 分发。
3. **20s 超时兜底** `markYufengChargePending`：客户端 249 未到（卡 UI/
   掉线）时自动补发阶段二，避免御风停在"只蓄力不生效"；取消御风时
   `cancelYufengChargePending` 清状态。
4. 保活帧改用 `protectedTimer`（计时器 panic 不再杀进程）。

### 验证与实测

`go vet` 干净；`TestQingGong|TestYufeng|TestBuff|TestNative|TestRecord|
TestSelfBuff` 全过（新增 249 对话断言：grant 后只有 ready 加 1 帧，
249 后真身加+ready 删+保活 3 帧、11611 到位）。构建通过。

实测步骤：重启服务端 → GM 加御风 → **等待蓄力条走完（约 2-10s）**，

## 第七轮：0xA9 原生 BufferStore 通道（根因之一，保留）

第六轮修复后实测仍失败：「御风状态二段跳还是普通的初级轻功」。日志显示客户端
全程只发 qinggong_9，从未发 qinggong_20——卡点在**客户端本地选择器**，还没轮到
216 处理。对 fxgamelogic.dll 反汇编（二段跳许可函数 0x1284EED0 + 御风/滑翔
门槛函数 0x1284F2D0）拿到终局实证：

1. **御风/滑翔门槛函数 0x1284F2D0 通过原生 BuffStore 管理器 vtable +0x2F8
   按 NAME 查询 HasBuff("buf_ride_yufeng")**，并反向排除 buf_qg_gliding。
2. 该原生 BuffStore **只由 0xA9（消息 ID 169，SERVER_CUSTOM 0x1E）Buffer
   增删帧驱动**。本服此前只下发 0x10 属性帧（BufferListStr/BufferInfo），
   原生 BuffStore 从未收到任何 buff → HasBuff 恒 false → 二段跳永远回落
   初级轻功 qinggong_9。第六轮加的 0x10 属性通道对这道门槛完全无效。
3. 旁证：客户端曾发 msg_id=1021 查询 buf_ride_yufeng，本服无处理——
   客户端确实在依赖原生通道。

### 本轮代码修复（全部在 cmd/protocol-probe）

1. **新文件 native_buffer.go**：按官服抓包帧（buf_ride_yufeng_ready /

   9 个 TVarList 值 = [int 169][int 0加/1删][string buff名][object 施加者]

   在 0x10 属性帧之后补发 0xA9 add/remove。**GM 加御风后客户端原生
   HasBuff("buf_ride_yufeng") 即为 true，二段跳进入腾跃。**
3. **链 buff 接入**（qinggong_records.go）：
   - activateQingGongBuff 补上第六轮遗漏的 0x10 属性帧下发（此前只 staged

## 第五轮：二段跳仍回落初级轻功的最终根因（IDA 交付包 + 运行版 DLL 双重实证）

第四轮补了 QingGongRec 六行后用户实测仍用不了。本轮通过运行版 DLL 的
字符串引用全量反扫（`artifacts/find_qg_xrefs_running.py` →
`artifacts/qg_xrefs_running.txt`）+ 反汇编 `artifacts/disasm_adv_selector.py`
拿到定论。注意：桌面 IDA 交付包基线与运行目录 DLL **不是同一文件**
（SHA B483… vs D9A5…，差 115KB），地址部分漂移，必须按字符串重定位。

### 根因

fxgamelogic **0x1284EED0**（二段跳进入大轻功的许可检查）逻辑：

1. 实体子类型字段 `[obj+0x5C0]` 必须为 0x88/0x8A；
2. 当前状态串与字面量 `"0"`（普通站地）比较，相等即拒绝（必须在空中）；
3. **按名读属性 `AdvancedQGFlyRushs`，要求值在 0..3 区间**（负数或 >3 直接
   返回 false）——服务端从未下发过该属性，get_prop 缺失返回负值 → 检查
   恒失败 → 二段跳回落初级轻功 qinggong_9；
4. `LogicState != 1`（战斗中不许）、地形检查（脚下有地面）。

同时 `skill_use_limit.ini` [560]/[561]/[562]（大轻功一/二/三段冲刺条件）
内容为：

```
[560] 一段：qg_must_air + CurQingGongType==20 + AdvancedQGFlyRushs==0 + buf_ride_yufeng
[561] 二段：qg_must_air + CurQingGongType==24 + AdvancedQGFlyRushs==1 + buf_ride_yufeng
[562] 三段：qg_must_air + CurQingGongType==24 + AdvancedQGFlyRushs==2 + buf_ride_yufeng
```

`CurQingGongType` 与 `AdvancedQGFlyRushs` 两个字面量在客户端所有 DLL 中都
**没有写入点**（CurQingGongType 甚至不存在于任何 DLL；AdvancedQGFlyRushs
只在 fxgamelogic 0x1284EED0 读取处 + fxprotect 各一次），客户端自身不维护，
只能由服务端属性同步下发。缺属性 → 冲刺技能 UseLimit 条件也全灭。

### 修复（全部服务端）

- `qinggong_records.go`：新增 `propAdvancedQGFlyRushs(361)`、
  `propCurQingGongType(362)`；
- `main.go`：0x09 属性表登记两个 FieldSpec（表尾追加，保持无空洞）；
  216 处理器维护链路状态：
  - 腾跃 `qinggong_20` begin → CurQingGongType=20、段位归零（新链）；
  - 一/二/三段冲刺 `qinggong_21/22/23` begin 被接受 → 段位推到 1/2/3；
  - 滑翔 `qinggong_24`/急降 `qinggong_25` begin → 只更新动作号；
  - 任意 GJ 动作 end 或初级轻功 begin → 链路状态清零；
  - 每次变更用 `qingGongStateUpdate()` 定点推两属性（不走全量档案，
    避免打断动作时间线）；
- `player_actor.go`：playerActor 增 `curQingGongType/advancedQGFlyRushs`
  字段 + 快照访问器；`stateProperties()` 初始下发 0/0（属性存在即通过
  0x1284EED0 的 0..3 区间检查）。

### 语义注记

- CurQingGongType = 当前 qinggong_N 的 **N**（20=腾跃 21/22/23=一/二/三段
  冲刺 24=滑翔 25=急降），与 use_limit 的 ==20/24 直接对应；
- AdvancedQGFlyRushs = 当前链内冲刺段位（0..2），一段冲刺（560）要求 ==0
  是在客户端本地检查（发送 216 qinggong_21 之前），服务端在接受 21 后才
  推到 1，时序自洽。

### 附：本轮反汇编方法沉淀

- 磁盘 DLL 被 Themida 抽走部分函数体（0x1280E7xx 一带是 int3 空洞），且
  与 IDA 交付包基线不是同一构建——按地址硬翻会得到假函数；
- 可靠路线：全库找 `qinggong_/buf_qg_/GJQingGongPoint/qg_no_` 等字串 VA →
  把 .text 当 int32 数组暴力扫 rip 相对位移（target = site+4+disp）→
  .pdata 归属函数 → 反汇编目标函数；capstone 线性扫描会被非法指令截断，
  不要用。

## 第四轮：腾跃被凌空踏虚抢占的原因

用户 22:51 已用含 qinggong_21 修复的新构建重启，但二段跳仍被初级轻功链
（凌空踏虚 → 扶摇步法）消费，腾跃不触发。

进一步实证：

- `skill_use_limit.ini` 560/561/562 判「当前动作」全部用**数字 Type**
  （`r=1,CurQingGongType,20/24,==`）；
- fxgamelogic.dll 里只有 `qinggong_21` 一个子动作字面量——因为 CheckLearn
  需要硬编码兜底名，其余动作名都是**运行时按记录行动作名拼接**再去
  qgdefine.ini 查 Type；
- 因此客户端的「已学轻功动作集合」直接来自 QingGongRec 的行。缺
  `qinggong_20`（腾跃/大跳，Type=20）时，二段跳找不到大轻功动作，
  就回落到初级轻功链——这正是「优先级冲突」的真相。

**修复**：`qinggongRecordOnlyIDs` 扩为 qinggong_20~25 全部六个子动作
（腾跃/一段冲刺/二段冲刺/三段冲刺/滑翔/急降，qgdefine.ini 151~200 行六节
齐全），只写 QingGongRec、不进 View 46。

## 注意：重启陷阱

## 第三轮：「未学习」最终根因（fxgamelogic.dll 反汇编定论）

用 capstone 反汇编 `bin64\fxgamelogic.dll`（脚本 `artifacts/dump_qg_literals.py`、
`artifacts/disasm_qg2.py`），从 `CheckLearn_QingGong` 交叉引用追到 0x11FD70A0
处的原生实现，逻辑为：

1. 对输入名做 16 字节 `repe cmpsb`，与 .rdata 字面量 `qinggong_gaojie`
   （0x12D6EAE0）比较；
2. **相等时把查询名替换成紧邻的另一个字面量 `qinggong_21`（0x12D6EAD0）**——
   即「高阶轻功」类别在客户端被原生映射为具体子动作
   「高阶轻功：一段冲刺」（qgdefine.ini `[qinggong_21]`，BufferID=buf_qg_airrush）；
3. 再到玩家记录集里查该名字，查不到 → `CheckLearn_QingGong` 返回 false →
   面板红字「未学习」。

此前服务端 QingGongRec 只发了类别行 `qinggong_gaojie`，从来没有 `qinggong_21`，
所以无论激活什么都显示未学习。

**修复**：新增 `qinggongRecordOnlyIDs = ["qinggong_21"]`，登录时随
`grantStarterQingGong` 写入 QingGongRec 记录（只进记录、不进 View 46，
避免武学面板多出无关卡片）；测试补断言 `QingGongRec 必须含 qinggong_21`。

## 问题

轻功类型里的「大轻功」（百鸟凌云系列：大鹏展翅/飞燕穿空/灵鹤御风/搜牛扑食，
对应 `QG_JH_gj_001` 等）无法使用；高阶轻功面板显示「未学习」、六系技能卡
图标空白且全部误显示「登峰造极」；激活按钮无法切换高阶轻功。

## 根因（客户端解包 + fxgamelogic.dll 字符串实证）

1. **御风状态是硬前置**：客户端 `skill_use_limit.ini` 条件包 560/561/562
   （大轻功一/二/三段条件）都要求 BuffStore 存在 `buf_ride_yufeng`。
2. **激活协议解析错误（核心）**：客户端「激活」按钮发的是
   `CLIENT_CUSTOMMSG_QG_SKILL(217)` 三值 `(217, sub, 技能ID)`，
   sub 1=激活 / 2=关闭 / 7=删除；旧服务端按两值解析（把 sub 当技能ID），
   所有激活请求都被当 malformed 拒掉 → 激活从未成功、无法切换、
   ActiveQGSkillRec 永远为空。
3. **View 46 技能对象缺属性**：图标按 `QGSkillStatic.Photo` 走 `StaticData`
   属性解析，旧对象只带 ConfigID → 图标全空；`Level/MaxLevel` 缺失时
   `Level(nil)>=MaxLevel(nil)` → 全部误显示「登峰造极」。
4. **高阶轻功值属性缺失**：fxgamelogic.dll 硬编码
   `GJQingGongPoint/MaxGJQingGongPoint/MaxGJQingGongPointAdd` 玩家属性
   （大轻功条 `pbar_gj_qinggong` 与冲刺门槛读取），服务端从未下发 →
   客户端视为 0，大轻功会被本地拒绝，「未学习」很可能也源于此。

## 修复内容（全部在服务端，未动客户端 Lua）

1. `handleActiveQingGongCustom` 按三值协议解析：sub1 激活 /
   sub2、sub7 关闭（`deactivateQingGongRecord`，0x12 删行，行号按
   `activeQingGongOrder` 维护）→ 六系高阶轻功可自由切换激活。
2. `qingGongViewProps`（View 46）：技能对象补
   `StaticData/ItemType/Level=10/MaxLevel=10`（qgskill.ini 懒加载）→
   图标正常、等级显示正常；类别对象保持单 ConfigID。
3. 字段表补 358/359/360（GJQingGongPoint 三件套），stateProperties 与
   普通轻功值同源下发 → 大轻功资源条有值。
4. 第一轮修复继续有效：GM 面板「御风神水（大轻功）」添加/取消御风状态、
   默认激活 `QG_JH_gj_001`（百鸟凌云）、补发 `QG_JH_gj_005`。

## 使用方法

1. 重启服务端并重新登录。
2. 高阶轻功页：百鸟凌云默认已激活；点其它系列的「激活」可切换
   （同时只有一套生效，激活新系会关闭旧系时按 sub=2 走删除行）。
3. GM 面板 →「御风神水（大轻功）」→ 添加御风状态（10 分钟）。
4. 空中两段跳后按轻功冲刺键施展大轻功；不需要时点「取消御风状态」。
