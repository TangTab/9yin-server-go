# 官服大轻功被动抓包报告

**抓包时间**: 2026-09-12 00:36:30 ~ 00:37:56 (约 86 秒)
**抓包对象**: 官服 fxgame.exe (PID 43328) ↔ 103.143.19.173:7061 (游戏服)
**抓包方式**: dumpcap 被动抓包（未修改任何服务端/客户端文件）→ tshark 导出 TCP 载荷 → official_decode.py 离线还原（EE 转义分帧 + InitialKey 0xFA6D3BCC 循环 XOR 解密）
**操作流程**: 使用御风道具 → 起跳 → 二段跳进入大轻功 → 多段空中冲刺

## 二、核心发现

### 发现 1：官服客户端二段跳发的是 qinggong_20 / qinggong_24，不是 qinggong_9

C2S op=0x0A 自定义帧，消息 ID **728 (0x02D8)**，参数为动作名字符串：

```
C2S: id=728  "qinggong_20"   ×1   ← 首次腾跃（大轻功第一段）
C2S: id=728  "qinggong_24"   ×3   ← 后续空中冲刺段
C2S: id=729  "qgskill_gj_air_rush_1_typ7" + float(10.46)  ×2  ← 特效请求
C2S: id=729  "QG_JH_gj_001"  ×1
```

**整个抓包窗口内客户端没有发过一次 qinggong_9。** 官服客户端在御风状态下二段跳直接走 qinggong_20 大轻功分支。

### 发现 2：全程没有 AdvancedQGFlyRushs / CurQingGongType / GJQingGongPoint 属性帧 ⚠️

在本次「用御风→大轻功」完整流程里，官服服务器**从未下发**这三个属性（0x09 属性帧零命中）。

结论修正：第五轮给我们服务端补发 361/362 属性的方向**不是关键门槛**。fxgamelogic 0x1284EED0 检查的 AdvancedQGFlyRushs∈[0,3] 是**客户端本地维护的冲刺段数计数器**（每次冲刺自增），不是服务器下发值。

（保留项：本次抓包开始时用户已登录在游戏中，登录包未覆盖；不排除登录期下发一次，需要时可重抓「从登录开始」的会话验证。）

### 发现 3：官服大轻功链路的 buff 序列（我们最可能缺的东西）

S2C op=0x1E 自定义帧，消息 ID **169 (0xA9) = Buffer 增删**，字段含 buff 名 + 双实体 GUID + 双时间戳 + int32 参数：

| 顺序 | buff 名 | 出现次数 | 尾部 flag |
|---|---|---|---|
| 1 | `buf_ride_yufeng_ready` | 2 | `02 00000000` |
| 2 | `buf_ride_yufeng` | 3 | `02 00000000` |
| 3 | **`buf_qg_gliding`** | **6** | **`02 00080000`** |

**`buf_qg_gliding`（滑翔 buff）是官服大轻功腾跃状态的核心标记**：每一段空中冲刺（特效 qgskill_gj_air_rush_1/2/3_typ7）之后，服务器都重新下发一次该 buff（尾 flag 带 0x08 位，与普通 buff 不同）。我们服务端此前从未下发过这个 buff。

伴随道具消耗帧（消息 ID 1，字符串 "11610" = 御风道具模板 ID）。

### 发现 4：服务器对每次冲刺的完整应答包（时序）

每次客户端发 728/729 后，官服服务器的应答序列（以第一段为例，frames.log L283~L293）：

```
1. op=0x1E id=205(0xCD) sub=4  播特效 "qgskill_gj_air_rush_1_typ7"（实体 GUID ×2）
2. op=0x10 vital 0x2b7/0x26f/0x1cc/0x2bc...  状态小整数（其中 0x2bc=700 的值
   随段数递增 2/3 —— 疑似当前冲刺段数）
3. op=0x10 vital 0x180 float 12.4→14.4 / 0x184 float 8.5→10.5 （疑似腾跃点数类数值）
4. op=0x10 vital 0x27a(634) LogicState 字符串:
   御风期:  "2924,E008E12,3A0E6E6,0,C37C20B4A5C,0"   （第 4 段 = 0）
   滑翔期:  "5A1E,E008E12,3A0E6E6,1,C37C20B7CF5,0"   （第 4 段 = 1 ← 腾跃状态位）
5. op=0x1E id=169 加 buf_qg_gliding
6. op=0x1E id=20(0x14) 携带特效名 + float 7.0 (0x40E00000)
   op=0x1E id=81(0x51) 三个 float（位置广播）
7. op=0x21 移动同步帧（双 float 三元组）
```

### 发现 5：vital(op=0x10) 通道的属性 ID 与我们第五轮用的 361/362 对不上

官服实时下发的 vital ID：`0x2bc(700)`、`0x180(384)`、`0x184(388)`、`0x27a(634)`、`0x2b7(695)`、`0x26f(623)`、`0x1cc(460)`。与我们按反汇编定的 358~362 不一致（可能存在编号偏移或两套通道）。**后续对齐应以这批实测 ID 为准。**

## 三、对我们服务端的整改方向（按优先级）

1. **补 buf_qg_gliding**：收到客户端 728 动作帧（qinggong_20/24/…）时，用已有的 0xA9 Buffer 通道下发 `buf_qg_gliding`（尾 flag 带 0x08 位），并在结束时删除。这是「没进入腾跃状态」最可能的缺口。
2. **处理 C2S 728/729**：登记消息 ID 728（动作名同步）与 729（特效请求），并按上面第 4 节时序回：205 特效广播 → vital 状态 → 169 加滑翔 buff → 20/81 位置效果帧。
3. **回退/降级第五轮的 361/362 属性补发**：保留无害，但不再作为修复点；改为核对 vital 0x2bc（段数计数）与 0x180/0x184。
4. **qinggong_20~25 记录下发（第五轮已做）保留**——官服客户端发 qinggong_20/24 的前提是已学集合里有这些记录，方向正确。
