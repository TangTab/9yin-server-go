## 症状
打开铁匠「冶炼」（466 已能弹表单）后，**把武器拖入洗练格 / 点开始**时报 `100059 当前活动未开启`（custom_sysinfo "100059"），洗练不可用。

## 根因（已二次定性，2026-09-08 凌晨）
客户端武器洗练表单 `form_recast_attribute_weapon.lua` 的门禁全部落在**原生 `SwitchManager`** 上：

- `open_form()`（1619-1634 行）**和** 开始/随机/定向按钮（334 / 577 / 715 行）都调 `CheckCurFuncStatus(op)` → `SwitchManager:CheckSwitchEnable(53)`（招式直接洗 op=9 走 2861）。
- `SwitchManager` 是 **C++ 原生单例**；line 1625 写明 `if open ~= true then return end`——**`CheckSwitchEnable` 必须返回 `true`**（不是 nil、不是 false），否则表单直接 return。
- D:\ 参考端能用的真正原因 = 客户端原生 SwitchManager 53 **从来都是 true**（未被任何服务端写入过禁用），native C++ 默认值就是 true。

**什么会把 53 写成禁用？——服务端发来的 S2C 413（`customOpenCheckSwitchEnable`）、原生 sync、原生 gamestep，会重建原生开关表并把 53/2861 写成 false。**

> 注意一个反直觉点：413 到 Lua 层走 `custom_handler.on_open_check_switch_enable` → `util_switch_function.on_query_switch`，但 **switch 53 不在其 `switch_func_tab` 表里**，所以「主动推一条 413(53,1)=1」在 Lua 层对 53 是**空操作、写不进本地表**；在原生层反而可能触发表重建/写禁用。因此「用 413 去刷缓存」既无效又有害。

### 本次错误修复的回滚（关键教训）
23:1x 曾在「打开冶炼后延迟推 S2C 413(53/2861/2923)=1」试图把缓存刷成开启，结果**正是它自己在 600ms 后把 53 写回禁用**——用户 23:21 实测仍 100059 即源于此。
