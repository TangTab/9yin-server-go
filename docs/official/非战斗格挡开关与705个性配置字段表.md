## 一、dump 分析

工具为临时件（`tmp/dmp_parry`，未入库）：

| 工具 | 作用 |
|---|---|
| `mdmp.py` | mmap 随机访问 minidump：模块 / Memory64List / MemoryInfoList / 线程上下文 |
| `blob.py` | 按字段表解码 107/705 串 |
| `gdis.py` | capstone 反汇编 rebuilt DLL（RVA == 文件偏移，基址 0x3af0000） |

dump 概览：189 模块 / 7929 段内存 / 67 线程，2.95 GiB。FxGameLogic 基址
`0x3af0000`，与 rebuilt DLL 同基址，内存可直接对拍。会话 = 我方私服
born03_YanYuZhuang（非官服）。

**开关的发现链**：

- 客户端文本表 `resources/text/chineses/interface.idres`：
  `ui_system_fight_fightingparry=非战斗状态可招架`，提示
  `勾选后不在战斗状态也可以招架`。
- `form_system_interface_fightfreedom.lua`：复选框 `cbtn_fightparry` 读写
  `game_config_info.fightparry`，存 `systeminfo.ini [Config]`；
  `game_config.lua` 默认 `fightparry = 0`。保存后调
  `customizing:SaveConfigToServer()`，即 107 上传。
- dump 堆内两棵 `std::map<std::string, 16B 值>` 红黑树（BFS 读出）：
  A = `[Config]` 键集 129 项（0x100c4ab0..0x100c8950），B = ini 全键
  注册表 267 项（0x100c1240..0x100d0870），均含 `fightparry`。
- 全 dump 搜按压差值 K（`0x11D5DA29`）的 imm32 字节零命中——K 不是字面
  常量，生成点仍在 VMP 区，未逆出（不影响服务端解码）。

**序列化器**（native）：lua 绑定表 `.data` rva `0x1e11ac8`
`{"SaveConfigToServer", ILT 0x40098}` → `sub_3EA040` → 函数体 `0x3EA066`：

```
lea rbx,[0x1dd8a20]   ; 字段表起   lea r14,[0x1dde210] ; 字段表止（134 行 × 0xA8）
loop: rsi = [rbx-0x18]        ; 键名
      r12d = [rbx]            ; 结构偏移
      if (config->HasProp(rsi)) struct[r12 + this+0x38] = config->Get(rsi) + 1
      rbx += 0xA8
struct[0x86] = 0              ; C 串终止符
send(struct)                  ; VarList{107, string}
```

值 = 配置值 + 1：`01` = 假/0，`02` = 真/1，`0x65` = 100
（`camera_angle`），`0x10` = 15（`max_camera_dis`）。S2C 705 的客户端
处理 `on_parser_customizing` → `customizing:UpdateToConfigObj` 原样灌回，
并**强制 `camera_value=0`、`game_control_mode=0`**。

## 三、官服抓包口径（初始账号登陆-任务-入门2）

**705 下发**：每次完整进场登录段恰 1 帧。切景段帧序 = `0x09 表 → 0x0A
记录帧 → 0x10 属性帧…→ m705（#4871）→ 属性帧 / 登录信息帧 → m414
gamestep(4,5) → 0x0B 进场 → shortcut_rec 0x14 挂载 + 0x29 批`。载荷与
上一发 107 逐字节相同；其后客户端的两发转储与 705 零变化（下发 → 应用
→ 回传一致）。

**107 上传**：全程零应答。

**键位 / 操作模式**：`m99 → 0x10 OperateMode=N`、`m195 → 0x10
ShortcutKey="<串> "`（尾空格）即时应答；登录段不下发键位串与 OperateMode
（全包键位串只出现在这两类应答与上传里）。

**三次真实变更对拍**：

| 时刻 | 操作 | 107 变化 |
|---|---|---|
| 20:49:33 | 操作模式切 2.5D（m99 i:1） | [6] `operate_control_mode` 1→2 |
| 20:53:59 | （设置变更） | [3] `mr_rotate_mode` 1→2 |
| 20:55:17 | 勾选「非战斗状态可招架」 | **[94] `fightparry` 1→2** |

**非战斗格挡应答簇**（20:55:18–22 连按 7 次，玩家 `LogicState` 全程 0）：

```
按下：InParry=1 → ParryUpSpeedAdd=-3 → m169(0,"BuffInParry") → InManualParry=1
松开：m169(1,"BuffInParry") → InParry=0 → ParryUpSpeedAdd=0 → InManualParry=0
```

无 LogicState 帧、无 MoveSpeed/RunSpeedAdd、无 BufferInfo2。m54 令牌：
该纪元基调 747265040349、按压 747564268038（差 = K），按压后 38ms 应答。
勾选之前的 13 分钟共 13 个纪元，m54 全是基调、零按压——与「开关在
客户端」互证。[官方女号抓包](初始女号抓包m54手动格挡全解.md) 记录的
「非战斗只置 InManualParry」是新手引导段与技能同发的特例；本包的
干净非战斗按压是 InParry 与 InManualParry 双置。

## 四、我方问题链（61 会话真机抓包实证）

1. **705 晚到、切图不发**：下行位只有首传闸 re-assert 一处，排在整个
   进场段约 1600 帧之后（S2C #1623）；切图重入不重发。
2. **登录期转储落库**：客户端每次完整进场都在 0x09 之前转储 2–3 份
   107。首传闸只挡首份，第 2/3 份照常落库。
3. **0x0D 只内嵌 ShortcutKey**：引擎建对象时即读整个键位域，缺
   OperateMode 时客户端的 `operate_control_mode` 被方案默认模式顶成 0。
   52103 会话服务端零 705 仍复现（#4 op=1 → #15 op=0，同时
   `one_key_active_jingmai` 0→1），键位串只出现在 0x0D（S2C #5）。
   随后第 2 份转储把 0 落库。

   实例：`62413`（20:40 用户设操作模式 = 1，4 发上传入库）→ `63308`
   （20:41 重登：#4 op=1，#14/#15 被顶成 0 并落库；705 仍是 1 但晚到）
   → `61114`（之后上传与 705 全是 0）。

4. 旧坏串期（11-22 13:07 – 11-23 20:27）：第 2 份转储里的
   238/190/188 = `EF BF BD`，即客户端应用了被 JSON 清洗的 705 后原样
   转储——[705 卡顿排查](自定义配置705推送卡顿排查.md) §七已修。

## 七、遗留

- **存量档可能持有被顶掉的旧值**（如 `operate_control_mode=0`、
  `fightparry=0`）：部署后首次进场的 705 会把客户端本地配置对齐到存档，
  需在设置里重设一次，此后保持。
- 官服非战斗应答簇带 `ParryUpSpeedAdd=-3` 与 `BuffInParry`；我方仍回
  三属性帧（战斗态真机验证过的方言），未逐字节对齐官服。
- 705 先于 0x0D 到达，而 0x0D 的键位方案在引擎建对象时加载——
  `operate_control_mode` 是否仍被顶掉，取决于内嵌的 OperateMode(223)
  是否被引擎建对象路径消费（参考端如此做且注释自证）。第 2 项验证
  若操作模式仍回到 3D，下一步是查 native 建对象时对 223 的处理。
