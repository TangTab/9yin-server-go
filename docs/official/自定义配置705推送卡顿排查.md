## 七、根因定案（2026-11-23 晚）

### 7.1 证据链

1. **候选 A 抓包逐字节**（65238/59345，`tmp/705dump`，临时件）：客户端首传
   107 是干净串——116 字节，尾部 `… 02 02 02 e5 02 02 01 02 01 05 …`；
   服务端 re-assert 的 705 是 144 字节，尾部
   `… 02 02 02 [EF BF BD] 02 02 01 02 [EF BF BD] 03 02 02 [EF BF BD][EF BF BD] …`；
   客户端收到后的两发上传与坏串**逐字节相同**。
2. **库值**：`nx_base.nx_roles`（account=test001 岳绮丝）`role_state_json.customizing`
   现存即坏串（`\u0001e…\ufffd\u0002…`，7 个 U+FFFD）。
3. **代码**：`rolestate.MarshalRoleState` = `json.Marshal(state)`；
   `encoding/json` 对 string 做合法 UTF-8 清洗——非法字节（这里是 ≥0x80 的
   配置取值）换成 U+FFFD，**一字节膨胀成三字节**。存档通道
   `role_state_json` 为 longtext（utf8mb3），也存不下原始字节。
4. **历史回溯**（`logs/capture` 56 个含 107/705 的会话）：
   - 11-21（功能上线前）：无异常。
   - 11-22 13:07 起：**每个会话**服务端下行的 705 都是同一条
     `len=144, EF BF BD×7` 的坏串；客户端首传多为干净串（1 或 7 个高字节），
     收到坏 705 之后的转储全部变坏；重登（未重启客户端）首传即坏串。
5. **干净串 vs 坏串**（57164 首传 vs 回推）：干净串尾部有 7 个高字节取值
   `161/129/145`（0xA1/0x81/0x91），如 `… 02 02 02 161 02 02 01 02 161 03 02 129 …`；
   回推坏串对应位置是 `239 191 189` 三连——原 1 个取值的位置被占成 3 格，
   其后所有字段依次右移（每遇一处再累积 2 格）。两者尾部其余取值并不相同
   （坏串是更早一次上传的损坏版本），说明库里的存档早已是旧配置的坏档。
   客户端按序取值的画面配置自此整体错位。
6. **与二分史自洽**：620f77a / 548e616 / 候选 A / debug 轮 4 都下行了坏 705
   → 卡；777c8e3 / debug 轮 3、6、7 都没下行 705 → 不卡。此前归因的
   「on_parser_customizing 控制对象重置链」只是伴生副作用。
