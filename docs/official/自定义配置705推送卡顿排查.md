## 二、线路抓包实证：客户端时序

数据源：部署目录 `E:\Game\9yin\9yin-server-go2\logs\capture\*_c2s.bin /
*_s2c.bin`（`internal/net/capture.go` 落盘的原始线路字节），11-22
14:50–20:36，共 162 个文件。抓包构建早于 777c8e3（23:31），即
**save-echo 尚开着**的版本——所以它反映的是**客户端**的收发节奏，
不是现行服务端的 705 数量。

解帧方法（可复现，脚本为临时件未入库）：`EE EE` 定界成帧、`EE 00` 还原
0xEE、整帧按 4 字节键 `CC 3B 6D FA`（InitialKey 0xFA6D3BCC，本服不换钥）
循环 XOR；0x1E 帧偏移 1、0x0A 信封偏移 21 起为 TVarList，首值 int 即
消息号（107 上传 / 705 下发）。

48 个进入过场景的会话（C2S 含 0x09）：

| C2S 时序形态（R = 0x09 ClientReady，数字 = 其前的 107 上传次数） | 会话数 |
|---|---|
| 3R | 31 |
| 4R | 13 |
| 2R | 3 |
| 3R2R（唯一一个完整切图，端口 55183） | 1 |

- **107 全部早于 0x09**：最后一次 0x09 之后还有 107 上传的会话只有 1/48。
  客户端每次进场景只发一发 0x09。
- **切图同样先上传再就绪**：55183 的 S2C `0x0C #6878 → 0x0B #6888 →
  0x0D #6889`，客户端随后 `107 ×2（C2S #1286/#1287）→ 0x09（#1291）`。
  另 17 个含 0x0C 的会话客户端只发过一发 0x09（抽查 5 个均为 0x0C 后无
  0x0B，切图未完成或下线退出），不可用。
- **705 有两个下发位**（55183 登录段）：第一发 `#3347` 紧跟进场段 0x28 帧海
  之后、视图容器 0x15（`#3446` 起）之前，即首传应答；`#3430/#3431` 是
  后续上传的 save-echo；`#3569` 在就绪簇内、战斗属性帧（`#3561` 起 0x10×8）
  之后、键位帧（`#3570`）/快捷栏行（`#3573`）之前。
- 该构建下每会话 S2C 705 数：最少 1、中位 4、最多 12（回显未禁）。

结论：ReadyFrames 里的 705 在 0x09 之后才下行，**必然晚于**客户端的登录
转储；能早于转储的只有首传闸那一发。

## 三、客户端对 705 的处理（lua64 直读）

- `resources/lua64/custom_handler.lua:3958-3980` `on_parser_customizing`：
  每收一帧 705 → `customizing:UpdateToConfigObj(customstr)` → 强制
  `game_config_info.camera_value = 0`、`game_control_mode = 0` →
  `save_game_config(…, "system_set.ini", "main")` → `Save_movie_config(false)`。
  前置：`customizing_manager` / `game_config` / `game_config_info` 任一无效
  即直接返回（该帧无任何效果）。
- 场景加载 `stage_main.lua:1111-1142` 重建 `game_control`：
  `CameraMode = get_camera_mode()`（`control_set.lua:8-19`，读 INI 的
  `camera_value`）→ `FightOperateMode` 随之为摇杆/普通，随后 `ResetCamera()`。
  即每次切图都按 INI 里的 `camera_value` 重建控制对象。
- **未验证**：`GetIniInfo("camera_value")` 读的是否就是 705 写的同一 INI
  节；`UpdateToConfigObj`（原生对象，无 lua 源）具体重建了什么；
  0x09 之前到达的 705 客户端是否真的应用（决定 §五分支 B 是否需要）。
