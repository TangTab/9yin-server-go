## 一、会话与工具链

- 主游戏会话：TCP **8032**（服务端）↔ 55496（客户端），c2s 228,416 B /

- 解码链：pcapng → TCP 双向重组（带每字节到达时间戳）→ EE 转义成帧 +
  InitialKey(0xFA6D3BCC) XOR → 帧事件流（C2S 0x0A/0x1E 自定义消息、
  S2C 0x09 属性表 2433 条 + 0x10 属性帧逐属性解码）。C2S 全程 3,809 帧

- **顺手修复 tools/pcapsplit 死循环**：EPB 分支 `if dir < 0 { continue }`
  跳过 `off += blkLen`，遇到任何非目标端口包（ARP/IPv6/其它 TCP）即原地
  死循环——此前能用的原因是老流程喂的是预过滤抓包。

## 二、C2S m54 消息形态

0x0A 活动信封（21B 头 = 0x0A + 16B 会话区 + u32 信封序号）携带 TVarList：

```
02 00            值计数 2
02 36 00 00 00   tag2 int32 = 54（消息号）
03 <u64 LE>      tag3 int64 = 令牌
```

全 197 条均为 `[i32(54), i64(token)]` 双值形；0x0A 信封同时承载
m9/m15/m924/m211 等活动消息，按首值分流。m54 无固定周期：闲时心跳
约 0.4-8.5s 不等（E1 段）或 1.3-2.5s（E3 段），按压/松开为即时上报。

## 三、令牌纪元与 K 形判别（本文核心）

197 条 m54 的值域共 14 个 u64，按时间切成 8 个「纪元」；**每纪元一个
基调 B（闲时/松开值），按压值恒为 B + 299,227,689（0x11D5DA29）**：

| 纪元 | 起始 t(s) | 基调 B | 按压 B+K | 出现次数 | 备注 |
|---|---|---|---|---|---|
| E0 | 118.100 | 5317501392 | — | 2 | 教程前期，无应答（格挡未启用） |
| E1 | 132.587 | 5226499786 | 5525727475 | 59+13 | 教学实操段，13 次按压 |
| E2 | 253.754 | 4667437540 | 4966665229 | 8+2 | |
| E3 | 362.738 | 7812541289 | 8111768978 | 22+9 | 11s 长按 9 连发 |
| E4 | 526.302 | 9382670946 | — | 6 | 无按压 |
| E5 | 593.040 | 7151281204 | — | 21 | 无按压 |
| E6 | 739.604 | 9235886144 | 9535113833 | 10+3 | |
| E7 | 825.214 | 2624970473 | 2924198162 | 15+3 | 首报即按压形（§六-3） |

- 六个有按压对的纪元差值全部 = 0x11D5DA29 → **K 是客户端构建常量**，
  非会话随机（男号抓包仅 2 条孤立基调、无按压对，不矛盾）。
- **令牌双向流零下发**：8 个基调 + 6 个按压令牌的 u64 小端字节在 c2s/s2c
  全流（裸态与 InitialKey XOR 态）均搜不到 → 令牌纯客户端生成，官服
  解码只能靠值形。
- **轮换触发器 = 副本切景**：每个纪元起点前 0.26-0.7s 必有
  `m1(3, id, 名, "ini\scene\cloneXXX", …)` 场景装载 + `m586(5)/m645(1)/
  m646(1)/m750(20)` 簇（E1 起点前是 m9 校验串 + m15 UUID 对）。14 分钟
  8 次轮换——**「首条基调永久锁存」的解码器在这种节奏下必然失效**。
- 上报模型（E3 定案）：状态心跳而非纯边沿——**长按期间 ~1.3s 周期重发
  按压令牌**（381.27→390.48 共 9 连发），松开后也重发基调（403.118/
  403.156/403.212 三连发）；官服对全部重发零应答，仅变迁应答。
- 官服解码器复原（197 条全量回放，官服 InManualParry 变迁 38 例命中 36，
  含长按 9 连发只算一次按压；2 例未命中均为 §六-3 的「轮换后首报即
  按压」形态）：
  - v == B → 闲/松开；
  - v == B + K → 按下/保持；
  - 其它（且非 0/1）→ 轮换新基调，采纳并复位，零应答（E0→E1→E2→E3
    四次轮换实测均零应答）；
  - 0/1 → fork 二值方言直判（0=按下；官服抓包不出现，兼容我们真机）。

## 五、ParryValue / LogicState 的真实语义（均非 ACK 成员）

- **ParryValue**：全 S2C 仅 7 帧——登录基线 `=72`（t=24.089，新号口径与
  我方 parryValueTotal 回退一致）+ t=225.8-232.9 的 `72→67→68→…→72`
  （格挡消耗一次 -5、脱格挡后 +1/s 回满）。**按值变更推送的耐力 meter**，
  不在按压/松开簇内；男号抓包另见 NPC 对象 74→86（+2/s）同机制。
- **LogicState**：全 23 帧、值域 {0,1,2}（另有一帧 104 疑似异义），与
  m54 变迁零相关（拔刀/战斗架势通道；成对出现在 350000f3 与伴生对象
  35000154 上，切景后成组 1→0）。**官服手动格挡完全不碰 LogicState**——
  我方 parry.go 的 LogicState=1 撑持是 fork 客户端方言（真机定版有效），
  与官服不同源，保留。

## 六、S2C「断流点」真相：一次 7 字节带外标记，非线路形态切换（已证伪）

初判「换形态」是误判，取证过程与定论：

1. **现场（t=522.802，流偏移 315431）**：干净 `EE EE` 终止符后插入 7 字节
   带外突发 `00 00 00 00 00 00 EE`（六裸零 + 单个 EE），随后 `DC 3B 9E FA
   CC 0E 47 …`。旧 framer 在标记尾部读到非法转义对 `EE DC` 硬停——这就是
   「断流」的全部原因。标记后首帧即教程换装槽 8 的鞋子应答（0x22/0x18
   含明文 "shoes_g0001"，对客户端 t=522.802 的 `m30(1,8,121,0)` 请求）。
2. **证伪换钥/换帧法/压缩**：从偏移 7 起用**原帧法 + InitialKey** 一路干净
   解到流尾（6,647 帧）；「ee 违法对」直方图与下一帧密文首字节的 op 分布
   完全一一对应（`d2:2671`↔op 0x1E:2671、`dc:1837`↔0x10:1836、`df:601`↔
   0x13:601 …）——全部是「终止符第二个 EE + 下一帧密文首字节」的扫描
   假阳性。标记跳过后全量 13,270 帧、非法转义恰 1 处、重同步恰 1 次。
   「失去 InitialKey 纹理」的观感来自标记后内容为字符串密集的属性风暴
   （零值少、键纹自然稀疏）。标记全流仅此 1 次（另一处 `00*6 EE` 匹配是
   帧内合法转义 `EE 00` 的假阳性）；C2S 全程无标记。
3. **上下文与语义推断**：标记落在 m30 换装请求与其应答之间（39ms），同
   毫秒客户端还发了 m9 反作弊串 + m15 UUID 对（切景前兆同款，E4 纪元
   3.5s 后开始）。客户端对标记零感知——C2S 心跳原节奏直通、无应答无
   重连，后续帧（m294/m1(“8052”)/0x38）正常消费 → 官方客户端的帧法带
   错误重同步（遇非法对丢弃到下一帧起点）。标记本体更像服务端换装/
   切景处理中的原始 flush 残片或带外心跳，非协商协议。
4. **E4+ 纪元就此全量可解**：E6/E7 按压簇与 E1 同构（按压
   MoveSpeed/RunSpeedAdd/InParry/m169/InManualParry，松开 m169 簇首+
   全清零；时延 39-130ms），仅 BufferInfo2/ParryUpSpeedAdd 两行缺席
   （末段场景 buff 模块变体）。**全量对拍：官服 InManualParry 变迁 38 例，
   我方 K 形解码器命中 36**；未命中 2 例均为 E7 t=825.214「轮换后首报即
   按压形」——官服在未见任何闲时上报的情况下正确回按压簇，证明其基调
   来源是**推导**（令牌字节从未上线，§三），纯线侧解码器原理上无法完全
   复现该例（我方按轮换采纳吞掉该次按压，下一次上报即自愈）。
5. **对工具链的启示**：decode_capture/propanalyze 遇此类标记会硬停；
   分析侧应带「非法对重同步」（丢到下一帧起点）。仓库 net 包的
   EscapeFramer 保持协议忠实不改——我方服务端不产这种标记，且重同步
   属于接收端容错策略，宜在分析工具层做。

## 七、与 parry.go 实现对照（检查结论）

保留项（有据）：
- 无变迁零帧 ✓（官服对长按重发/松开重发/闲时心跳全零应答）；
- ParryValue 总量 72 回退 ✓（登录基线一致）；
- 0x0A 信封解析与 m54 分流 ✓（m54probe_test 官方帧锚）；
- LogicState 撑持、三属性合帧、不用 m169/速度族 —— fork 客户端方言
  （官方形态在 fork 真机 415 条 m54 无反应的实证记录在案），保留。

修正项（本轮落码）：
1. **基调轮换误判（P1）**：旧实现首条基调永久锁存，官服族 14 分钟 8 次
   轮换后闲时心跳全量误判为按下 → 幻影格挡 + LogicState=1 永不回 0。
   新实现按 §三官服解码器复原：B+K 形按压、异值采纳、长按重发零帧。
2. **fork 二值方言 0/1 直判落实（P2）**：旧注释宣称「0/1 直判」但实现
   是纯基调差——首报若为 0（哨兵撞车）基调锁 0 后永久反判。新实现
   值域 {0,1} 走直判分支 + 首报 0 锚定空闲值 1。
3. 测试：TestParryStateReportBaseline 补长按重发/松开重发零帧；
   TestParryBinaryDialect 补首报 0 反判防护；新增 TestParryBaselineRotation
   （轮换采纳/持按轮换复位/新纪元按压）。`go test ./internal/fssoloworld/`
   全绿；197 条抓包回放对拍官服 InManualParry 变迁 38 例命中 36（§六-4）。

遗留观察（未落码，待真机/后续）：
- 我方 fork 客户端按压值是否恰为 1+0x11D5DA29（同 exe 同 K 预期成立，
  真机 trace 一行即可定案；若不符也只是退回「异值采纳」路径多一次
