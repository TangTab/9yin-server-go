### 9.2 c71 的线路形态与客户端槽位

挑战包里 c71 只有两种字节形态（`02` i32、`08` 对象、`06` 串、`04` f32）：

```
首波    1e 0c 00 | 02 18000000 | 08 <目标>   | 02 47000000 | 08 <目标>   | 06 0100000000 | 02 01000000
                  | 08 <施法者> | 04 0000f041 | 04 00000000 | 06 0100000000 | 04 00000000 | 06 0100000000
后续波  1e 0a 00 | 02 18000000 | 08 <上一目标>| 02 47000000 | 08 <目标>   | 06 0100000000 | 02 01000000
                  | 08 <施法者> | 04 0000f041 | 04 00000000 | 06 09000000 "qzj_07_2\0"
```

客户端处理函数（本地 `fxgamelogic.dll` `0x12a071f0`、外服 `0x50964e0`，两版逐指令一致）拿到
的是 m24 去掉前三个值后的子表，下标固定。按 m24 数组下标（首位 24 记作 0）对照：

| 下标 | 首波 | 后续波 | 客户端的槽 |
|---:|---|---|---|
| 1 | 目标 | 上一目标 | 处理函数的首参：这个对象转成的字符串，对应位移起点 |
| 3 | 目标 | 目标 | 终点对象；它的位置写进施法者的 `flash_end` |
| 4 | `''` | `''` | 名称参数，原样传给位移启动调用 |
| 5 | `1` | `1` | **必须为 1**，否则处理函数直接返回 |
| 6 | 施法者 | 施法者 | 下面各项都设到它身上 |
| 7 | `30.0` | `30.0` | `tm_speed`（m/s） |
| 8 | `0.0` | `0.0` | `tm_add` |
| 9 | `''` | `'qzj_07_N'` | `tm_action`：施法者的位移动作名 |
| 10 | `0.0` | — | `tm_back_dist`；子表超过 8 个值才读，否则取 0 |
| 11 | `''` | — | `tm_behit_action`；子表超过 8 个值才读，否则取空串 |
| 12 | — | — | `tm_stop_time`；子表超过 9 个值才读，官服从不发，客户端取 1.0 秒 |

所以「首波不发动作名、后续波 `_2`..`_8`」不是方言选择，而是官服利用了客户端的缺省：首波把
子表凑满 9 个值（动作槽留空），后续波只给 7 个值、动作名紧跟 `tm_add`。后续波形态里若在
`tm_add` 后面先补一个空串再放动作名（此前我方发的 11 值形态），动作名就落到下标 10 的
`tm_back_dist` 槽，客户端按浮点读它，`tm_action` 仍是空。

两个对象的线位（起点 / 终点）是按落点对上的：终点恒等于 m914 落点，起点恒等于施法者当时
站的位置（上一跳的目标）。处理函数查对象那一步的键构造没有完全读懂，见附录 §五。

### 9.5 锁态链与 CantParry 的读数

锁态链五个属性：`CantBeSkillLocked`、`CantParry`、`CantBeSkillMustLocked`、`CantBeAttack`、

| 施放 | 受理 / 每波置位 | 波间清除 | 收束 |
|---|---|---|---|
| 260.021、406.799、424.735、474.075 | 1 | 0 | 0 |

- **自身 buff `buf_CS_jh_hyjf08_03`**（StaticData 9019，寿命 1000ms）：受理时挂，每波重挂，

- **目标 buff `buf_CS_jh_hyjf08`**（StaticData 8925）：每波挂到当波目标身上（来源 = 施法者，

- **`buf_CS_jh_hyjf08_02`**（StaticData 8934）：官服另有一个不发 m169、也不发槽串的静默 buff，

### 9.7 旧解码里的「零头帧 / 0xCC 帧」是伪影

成因有两层。其一，S2C 方向的纯 ACK 被以太网填到 60 字节；其二，旧解码器的 TCP 重组没有
裁到 IP 总长，把这 6 个填充零字节当成载荷。流里的偏移从此错 6 字节：下一帧真数据的前 6 字节
被当成「重传」丢掉，于是出现「明文以 6 个零开头的帧」（零头帧）和 `op=0xCC` 的乱帧。

体检数据（`flashscan.py padding`）：

| 抓包 | S2C 报文 | 纯 ACK | 带零填充 |
|---|---:|---:|---|
| 挑战.pcapng | 3662 | 539 | 566（纯 ACK 537 + 小数据包 29） |
| 技能.pcapng | 6770 | 1248 | 1324（纯 ACK 1247 + 小数据包 77） |
| 技能4.pcapng | 3869 | 738 | 761（纯 ACK 738 + 小数据包 23） |
| 技能5.pcapng | 1974 | 181 | 188（纯 ACK 181 + 小数据包 7） |

C2S 方向没有填充。`tools/pcapevents` / `tools/pcapsplit` 现在按 IP 总长裁剪（`trimIPTotal`）；
裁剪后这四个包里 `op=0xCC` 帧为 0（旧解码：挑战 516 个、技能 2110 个）。技能1 在 594.121s
有一对首字节 0xCC 的大块（S2C 544357 字节、C2S 83743 字节，两个方向同时出现，正文全是密钥
重复即明文全零），前后紧接正常帧，不属于帧流，没有深究。

由此受影响的旧结论：m914 回显是 39/39（不是 36/39）；m294 是每秒一次的心跳应答（挑战包
518 条），与位移无关；《[冲锋与打坐外服方言总集](冲锋与打坐外服方言总集.md)》§2.5 说的
「c61 被 0xCC 吞帧」，在干净解码里 kfkj02 358.132 那一招走的是暂存簇（CurSkillID →
CurSkillTarget → m25 skill_pause → PauseSkill → m707 15），受理处本来就没有 c61。

### 9.8 m24 17 的第 5 值 = skill_static 的 DamageType

伤害帧 `m24 [目标 17 <伤害> 0 <X> <技能> <技能类别> <目标名> …]` 里的 X，此前我方恒发 0。
五个抓包 36 个技能逐一核对：X = 该技能在 skill_static 里的 DamageType（寒心恨雪 = 2）；由 buff
触发的伤害帧用的是源技能的 DamageType。`official` 分支的 `hitNPC` 已改为按定义下发。

   交给「子码 → 处理函数」表。分发器本体给出了合法子码范围与表基址：本地 1..98、外服 1..95，
   两版有处理函数的子码里只有 6 个引用的字符串不同（附录 §三）。
2. **子码 71 = 闪击**：处理函数引用 `flash_end / tm_speed / tm_add / tm_action / tm_back_dist /
   tm_behit_action / tm_stop_time / need_re_init_flash_attack / player_flash_attack`，取值下标见
   §9.2。设完属性后：施法者已是 123 号状态就只置 `need_re_init_flash_attack`，否则经状态机的
   `vt+0x58` 切到 `player_flash_attack`（123）。两版客户端这段逐指令一致，没有被虚拟化。
3. **玩家状态机的状态表**：状态机逻辑在 FxProtect.dll 里，被 VMProtect 虚拟化，三个版本的
   镜像里都读不出迁移代码；但运行期的状态注册表在 dump 的堆上完整保留——141 项、索引 1..141
   连续，123 = `player_flash_attack`，124 = `player_flash_stop`（附录 §二）。状态名和每个状态的
   日志格式串（`player_state_<状态> PLAYER_INPUT_<输入>`）以明文留在同模块的 VM 常量区。
4. **`IsFlashAttack`**：skill_static 里 12 个技能标了 1（寒心恨雪、`CS_jh_tqjf08` 等，附录 §六）。
   它只是数据标记——服务端技能表里没有这个字段，客户端二进制里也没有以它为名的串。
5. **取证方法**（三个版本通用）：.pdata 在这些 DLL 里不可靠（函数被拆成碎片），函数边界改用
   int3 填充定界；`.text` 起始处是增量链接的跳转桩表（`E9 rel32`），调用目标要穿透桩再配对；
   注册表之类的「取地址 → 写表」要按同一寄存器配对，不能假设相邻（曾因此把 61 / 74 / 78 / 79
   四个子码的处理函数配错）。

## 十二、工具与复现

```bash
# 1) 解码：必须用带 trimIPTotal 的 tools/pcapevents（§9.7），并开全帧 hex
NINEYIN_PCAP_HEXALL=1 NINEYIN_PCAP_HEX=4000 \
  go run ./tools/pcapevents <抓包.pcapng> <服务器端口> dumprec > dump.txt

# 2) 抓包分析：tools/pcapflash/flashscan.py（纯标准库）
python -I tools/pcapflash/flashscan.py flows    <抓包.pcapng>...          # 抓包里的 TCP 流，找服务器端口
python -I tools/pcapflash/flashscan.py padding  <抓包.pcapng> <端口>       # 纯 ACK 填充体检
python -I tools/pcapflash/flashscan.py casts    dump.txt                   # 施放总表
python -I tools/pcapflash/flashscan.py waves    dump.txt                   # 逐跳位移表（§9.1）
python -I tools/pcapflash/flashscan.py cast     dump.txt 474.075 4.8       # 一次施放的帧时间线（§9.4）
python -I tools/pcapflash/flashscan.py echo     dump.txt                   # m914 回显（§9.3）
python -I tools/pcapflash/flashscan.py m914     dump.txt...                # m914 的类型 / 计数位
python -I tools/pcapflash/flashscan.py timeline dump.txt <t0> <t1> [正则] [行宽]
#    其它闪击技加 --skill <技能 id>

# 3) 客户端二进制 / 内存 dump：tools/clientbin（pe.py / mempe.py / mdmp.py / subtab.py / stateconst.py）
#    用法与再生成命令见《客户端逆向数据附录》§一
```

`pcapevents` 的两个环境开关：`NINEYIN_PCAP_HEXALL` 在每条 A 行前多打一条带整帧明文 hex 的
H 行（S2C 默认不打）；`NINEYIN_PCAP_STREAMDIR=<目录>` 把两个方向的重组流各落一个 `.bin`。
